Four ways to search 2048 words

The BIP-39 English list is small, fixed and famously fiddly. People open it under three quite different pressures: checking a word they half-remember off a metal backup, transcribing someone's handwriting, or learning how the list is built. A substring filter serves none of them well.

So the search here is a ladder of match reasons — position, shape, spelling distance, sound, and meaning — and every result says which rung it came in on. Below are four ways to render that same engine. All four are live: type in the bar and they all respond to the same query.

  • starts with
  • contains / letters in order
  • 1–2 edits away
  • sounds like
  • related meaning

⚠ Never type a real seed phrase into anything. The app is a static, offline word reference — no network calls, no storage, no phrase field. That constraint is a design input, not a disclaimer: there is deliberately nowhere in this UI to enter twelve words in a row.

Console

CONCEPT 03

Field

All 2048 words at once, one cell each, in list order. Cells light in their match reason's colour and dim when they drop out — so you watch the candidate set collapse as you type, and see where in the list the survivors sit.

Wins atScale and teaching. It makes 2048 a felt quantity, and shows alphabetical clustering — a prefix search lights one contiguous band.
CostsCan't be read on its own; it's a companion view, not a result list. Hover-only detail needs a tap equivalent.
ReuseLow — entirely new. But it's the one view no other BIP-39 tool has.

CONCEPT 04

Orbit

The word detail view, not a search view. The best match sits at the centre and its neighbours hang off five spokes — one per relation. Click any neighbour to re-centre on it and walk the list by association.

Wins atAnswering "what else is near this word?" in one glance, and making the relation taxonomy self-explanatory.
CostsLayout is fragile with long words and thin screens; below about 480 px it has to fall back to stacked bands.
ReuseLow, but it only has to work on one screen — the word page the other three concepts all link into.

How "related" is actually computed

Every rung is cheap enough to run over all 2048 words on each keystroke — the whole pass is a few hundred microseconds, so there is no debounce and no index to keep warm. Only the last rung needs data that isn't derivable from the list itself.

RungWhat it catchesMethodData needed
exact The word itself. Equality. —
starts with Normal typing. Also the property BIP-39 guarantees: every word is uniquely identified by its first four letters, so at four characters this rung returns exactly one word. startsWith. —
contains Half-remembered middles and endings — -tion, -able. includes, excluding prefix hits. —
letters in order Skipped letters and shorthand: abndn → abandon. Subsequence scan, ranked by how tightly packed the run is. —
1–2 edits Transcription slips — swapped, dropped, doubled or wrong letters. recieve → receive. Damerau–Levenshtein with early cutoff; budget 1 edit up to four characters, 2 beyond. —
sounds like Dictation and accents: krane → crane, gost → ghost. A phonetic key — English digraph rules, then consonants folded into classes and vowels into one. Words sharing a key sound alike. —
related meaning The real ask: bird → eagle, owl, nest, wing. Also lets you search by category name. Anchor on the best letter-match, then return words sharing its topics, most specific topic first. The anchor has to be confident — a strong rung, and it must start like the query or sound like it — or meaning stays silent. That is why ocen reaches the sea but the fragment tion doesn't drag in lion's animals. A semantic index. See below.

What's running on this page

A hand-built topic index: 40 topics covering 677 of the 2048 words. Enough to judge the interaction, not enough to ship. Everything else above is the real algorithm over the real list.

Proposed for v1

Generate the index offline and commit it: WordNet synsets and hypernyms restricted to the 2048 words, plus the top 12 embedding neighbours per word. Ships as one static JSON of roughly 120 KB — no runtime model, no API.

Why not just embed at runtime

A model in the browser costs megabytes and a warm-up for a fixed 2048-word vocabulary whose neighbours never change. Precomputing is smaller, instant, reviewable in a diff, and keeps the app fully offline.

Design tokens

The same custom-property block: teal #4ecdc4 on #fafafa, 12 px radius, the two-step shadow, prefers-color-scheme dark, BEM-ish class names, system UI type. The screens above use those values verbatim.

One addition this subject needs: monospace for every word and number, because the words are material to be compared letter by letter — and the five relation hues, which are information, not decoration.

Simpler in one way — this app has no database, so there is nothing to snapshot and the backup/restore half of the script drops out.

Recommendation

Don't pick one. They aren't four apps — they're four views of one engine, and each covers a different pressure. Ship them as one screen with a view switch.

  1. Roster is the shell. Header lockup, tab bar and card grid come across from CountRoster, so the app looks finished on day one and the default view is the friendly one.
  2. Console is the results list behind a density toggle. Same data, same reason colours, ten times the words per screen — and it's the view that serves seed recovery.
  3. Field is a collapsible strip above the results, off by default. It costs one line of state and it's the thing people will screenshot.
  4. Orbit is the word page every card and row links into, with a stacked-band fallback under 480 px.

Open questions before I build

QuestionMy default if you don't care
Packaging — does this need CountRoster's Go binary and systemd unit, or is it a static bundle you drop on any host? Both: a static bundle, plus a tiny Go binary that embeds it, so the QuickStart story survives. No database, no API.
Stack — match CountRoster's Vite + React + TypeScript, or keep it dependency-free? Vite + React + TypeScript, mirroring apps/web, with Vitest for the engine.
Semantic index — WordNet, embeddings, or a curated topic list you can edit by hand? WordNet plus embeddings, generated by a committed script, output committed as JSON so it's reviewable.
Scope of the bits view — index and binary only, or the full checksum explainer? Index, hex and 11 bits per word. No phrase-level entropy tooling, which would mean a field people put real words in.
